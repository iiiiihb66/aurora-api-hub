# 🚨 极光 API (Aurora API Hub) 商业化交付核心痛点与待解技术命题

> **文档目的**：给外部协作者、架构师或其他大模型（如 ChatGPT / Claude / DeepSeek）阅读。  
> 详细陈述目前项目在进行**“个人免资质支付 ➔ 自动化发卡（一单一密） ➔ 防白嫖闭环”**时遇到的真实瓶颈与工程挑战，寻求最优技术方案。

---

## 1. 业务目标与交付场景

- **项目属性**：基于 Node.js / Express 开发的独立 AI 算力中枢，对外提供标准 OpenAI 兼容接口（`/v1/chat/completions`）。
- **商业模式**：
  - 售卖多梯度算力包（如：1元 30万 Tokens、5元 200万 Tokens、15元 700万 Tokens、29.9元 1600万 Tokens）。
  - 后台维护一个虚拟卡密库（格式形如 `sk-aurora-xxxx`），买家购买后使用该 Key 调用接口，按消耗的 Token 真实扣减。
- **交付铁律**：
  1. **一单一密**：每个买家付款后，必须获得**属于自己的、独享额度的独立 API Key**，绝不能所有买家共用同一个 Key。
  2. **24 小时无人值守全自动发货**：不依赖卖家在电脑前手工复制私信。
  3. **防恶意白嫖/爆破**：任何未实际付款的人，绝不能通过任意手段免费套取/猜走卡密库中的 Key。

---

## 2. 现实约束与踩坑历程

我们尝试了国内独立开发者常用的两大免企业资质收款平台（爱发电、面包多），均发现了致命的产品断层：

### 2.1 爱发电 (Afdian) 的阻碍
- **现状**：爱发电按月赞助机制根深蒂固。要使用其原生“商品卡密池（买家付款后屏幕自动弹码）”，**强制要求创作者必须完成平台认证**（提供 B站/GitHub/知乎 粉丝或项目证明）。
- **死胡同**：未认证的新账号，买家付了款后，平台只给一张“付款成功”收据，官方默认要求创作者在后台人工一条一条给买家发私信发货，**无法做到开箱即用的无人值守自动发货**。

### 2.2 面包多 (Mianbaoduo) 的阻碍
- **现状**：面包多虽然个人绑定支付宝即可收款（零资质门槛），但其本质是一个“付费阅读 / 附件下载”平台。
- **致命缺陷**：**面包多官方至今没有“卡密库”（即：后台导入 100 张卡密，买家每买一次自动扣除并吐出不同卡密）的原生功能**。
  - 如果在【付费内容】里直接写死一个 Key（如 `sk-aurora-xxxx`）：所有付了 1 元的买家看到的都是同一个 Key，算力被大家共用踩踏，商业逻辑不成立。
  - 如果在【付费内容】里放同一个下载附件：同样所有人下载的是同一个凭据。

### 2.3 当前采用的自建自提方案及“新安全漏洞”
为了绕过面包多的缺陷，我们设计了**【官网订单自提中心 (`/claim`)】**：
1. 面包多的【付费内容】中不写 Key，而是引导买家点击极光提卡链接：`http://localhost:3005/claim`；
2. 买家在页面上输入自己的【面包多付款订单号】；
3. 网关验证订单号，若第一次输入，则从卡密库提取一张全新 Key 强绑定该订单；若该订单重复查询，只返回同一张 Key。

#### 💥 遇到的核心致命问题（当前阻塞点）：
> **“买家输入的订单号，我无法在服务端实时校验真实性！”**
- 面包多的订单号是一串数字（如 `20260910...`）。
- 如果黑客或懂代码的用户写一个简单脚本，随机生成数字/字符串批量请求 `/api/card/claim`，由于我们服务端没有连接面包多内部订单数据库，无法核对该订单号到底有没有真金白银付款，**攻击者可以不花一分钱，几秒钟内把我们卡密库里的几十张 Key 全部瞎猜并提取一空！**

## 3. 待求解的核心问题 (Open Questions for AI / Architects)

请针对以上真实场景与约束，给出专业、成熟、已被商业验证的架构解法：

1. **在不使用传统企业资质 / 独立个体户繁琐域名备案的前提下**：
   - 国内独立开发者做“一单一密、自动发码”的虚拟数字商品（如 API Key、游戏激活码），目前主流、合规、体验最好的支付与交付方案到底是什么？
2. **针对面包多 / 爱发电**：
   - 是否有可靠的 Webhook 或免资质 API 回调手段？如何优雅地确保“买家必须真付了款，服务器才能验证通过并吐出 Key”？
3. **如果完全不依赖面包多/爱发电**：
   - 市面上是否存在既支持个人/免签微信支付宝收款，又天生自带成熟“卡密库存自动派发”的平台（且不被微信/支付宝风控拦截）？
4. **如果在现有的自提架构上优化**：
   - 如何以最小的改动，彻底解决“订单号防瞎填、防刷、防白嫖”的机制？

## 4. 关键过渡期背景补充 (Interim State: Business License Pending)

> **最新现状补充**：  
> 创作者**已经提交了个体工商户执照的申请**。  
> 但从“工商执照下发 ➔ 刻章/开户 ➔ 微信商户号/支付宝当面付开通 ➔ 网站工信部 ICP 备案与域名过白”，通常需要 **1 ~ 2 周的审批周期**。  
> 
> **亟需探讨**：  
> 在个体户执照与正规商户收款**还没彻底下发、尚未就绪的这一两周空档期**内：  
> 个人独立开发者应该采用什么“过渡期策略”，既能立刻把产品拿出去做 MVP 验证、接受第一批真实用户付费，又不会在发卡安全和风控上暴雷？
